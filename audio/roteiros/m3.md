# Roteiro de narração · Módulo 3

| Arquivo | Texto para narrar |
|---|---|
| `m3a1-01.mp3` | Pedir tudo de uma vez e torcer funciona às vezes. Este vídeo mostra um fluxo que funciona em qualquer tarefa que não seja trivial. |
| `m3a1-02.mp3` | Quando você pede: adicione prazos às tarefas, de uma vez, o Claude escolhe sozinho onde mexer, o formato da data e o que conta como pronto. Se errar, você descobre tarde. |
| `m3a1-03.mp3` | A saída é separar o trabalho em quatro etapas, com uma pausa entre elas, para você corrigir o rumo enquanto ainda é barato. |
| `m3a1-04.mp3` | Na prática: explorando, você só pergunta e avisa que não é para mudar nada. Planejando, usa o barra plan. Codando, pede para rodar os testes. E antes do commit, revisa o diff. |
| `m3a1-05.mp3` | Um ponto essencial: dê ao Claude algo que responda passou ou falhou, como os testes. O Claude para quando o trabalho parece pronto. Com testes, ele fecha o ciclo sozinho. |
| `m3a1-06.mp3` | Corrigiu a mesma coisa duas vezes e continua errado? Não insista: use barra clear e faça um pedido novo, mais completo, com o que você aprendeu. |
| `m3a1-07.mp3` | Mudança pequena e óbvia? Peça direto. Tarefa que não cabe numa frase? Use as quatro etapas. |
| `m3a2-01.mp3` | Plan mode: o jeito de garantir que nenhuma linha muda antes de você concordar com o caminho. |
| `m3a2-02.mp3` | Pedir: ainda não mude nada, funciona, mas depende de o Claude respeitar. No plan mode, as edições ficam bloqueadas até você aprovar o plano. |
| `m3a2-03.mp3` | Três jeitos de entrar: Shift Tab até aparecer plan mode on, o comando barra plan com a tarefa, ou abrir o Claude já com o modo plan. |
| `m3a2-04.mp3` | Em plan mode, o Claude pode ler arquivos, buscar no código, investigar e escrever o plano. O que ele não pode é editar seus arquivos antes da aprovação. |
| `m3a2-05.mp3` | Com o plano pronto, você escolhe: aprovar e deixar executar, aprovar revisando cada edição, que é o recomendado enquanto aprende, ou continuar planejando. |
| `m3a2-06.mp3` | Na tela de aprovação, Control G abre o plano no seu editor para ajustar. Cuidado: ali, Shift Tab aprova o plano. Para sair sem aprovar, aperte Esc primeiro. |
| `m3a2-07.mp3` | Mudança grande ou código que você não conhece? Comece pelo plan mode. |
| `m3a3-01.mp3` | Spec Driven Development: escrever o que você quer antes de pedir o código. É o método que deu origem a este curso. |
| `m3a3-02.mp3` | O Claude não lê a sua mente. Quando falta informação, ele preenche a lacuna com a suposição mais provável. E ela nem sempre é a sua. |
| `m3a3-03.mp3` | Uma boa spec tem cinco seções curtas: objetivo, requisitos numerados, o que fica fora de escopo, critérios de aceite e casos de borda. Uma página, não um tratado. |
| `m3a3-04.mp3` | Os critérios de aceite são verificáveis, no formato: dado, quando, então. Na próxima aula, cada um deles vira um teste. |
| `m3a3-05.mp3` | Você não precisa ter tudo resolvido. Peça para o Claude te entrevistar: ele faz perguntas, geralmente de múltipla escolha, até conseguir escrever a spec. |
| `m3a3-06.mp3` | Com a spec escrita, comece numa sessão limpa e peça: implemente a spec. No fim, revise contra o mesmo documento, focando em correção e ignorando estilo. |
| `m3a3-07.mp3` | A spec é o contrato: o Claude implementa, testa e é revisado contra o mesmo documento. |
| `m3a4-01.mp3` | TDD com o Claude: o teste vem antes do código e vira a verificação objetiva de que o trabalho terminou. |
| `m3a4-02.mp3` | O ciclo tem três cores. Vermelho: o teste falha. Verde: o código faz passar. Refatorar: melhorar sem quebrar. |
| `m3a4-03.mp3` | Os testes saem direto da spec: cada critério de aceite, dado, quando, então, vira um teste. |
| `m3a4-04.mp3` | Com I A, existe um risco específico: o caminho mais curto para tudo verde é mudar o teste, não o código. Por isso os testes são commitados antes, e o Claude não pode alterá-los. |
| `m3a4-05.mp3` | O roteiro: peça só os testes e confirme que falham pelo motivo certo. Revise e faça commit. Peça a implementação sem alterar os testes. E confira com git diff que eles ficaram intactos. |
| `m3a4-06.mp3` | Teste que depende da data real passa hoje e falha amanhã. Peça que as funções recebam a data de hoje como parâmetro, para o teste controlar o tempo. |
| `m3a4-07.mp3` | Resumindo: teste primeiro, travado. Depois o código. |
| `m3a5-01.mp3` | Verificação e revisão: como trocar o: está pronto, por evidência. |
| `m3a5-02.mp3` | Todos os testes passam, é uma frase. A saída do python traço m unittest é evidência. Essa diferença separa confiar de verificar. |
| `m3a5-03.mp3` | Revise o diff com método: primeiro, quais arquivos mudaram. Depois, linha a linha. E sempre pergunte: faz o que a spec pede? Só o que a spec pede? |
| `m3a5-04.mp3` | Quem escreveu o código tende a concordar com o próprio raciocínio. O barra code review é um segundo par de olhos: revisa as mudanças procurando bugs, sem ter visto a conversa. |
| `m3a5-05.mp3` | No terminal, a revisão roda em segundo plano e segue o seu Claude ponto MD. As correções do fix em segundo plano ficam fora do barra rewind: para desfazer, use o Git. Mais um motivo para commitar antes. |
| `m3a5-06.mp3` | Confiar é bom. Verificar é obrigatório. |
